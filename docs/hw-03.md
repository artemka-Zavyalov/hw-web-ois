# Практика 3 — ограничения, запросы и конкурентный доступ

## 1. Три запроса, которые база должна отклонить

Ниже приведены запросы для PostgreSQL. Перед выполнением каждого запроса база уже должна
быть заполнена данными из `db/seed.sql`.

### 1.1. Оценка 6

Оценка должна быть только от 1 до 5, поэтому `CHECK` отклоняет вставку.

```sql
INSERT INTO reviews (event_id, user_id, rating, text)
VALUES (1, 6, 6, 'Слишком высокая оценка');
```

Ожидаемый вывод PostgreSQL:

```text
ERROR:  new row for relation "reviews" violates check constraint "reviews_rating_range_chk"
DETAIL:  Failing row contains (3, 1, 6, 6, Слишком высокая оценка, ...).
```

Точный хвост `Failing row contains` зависит от версии PostgreSQL и фактического значения
`created_at`, поэтому при сдаче его лучше заменить на вывод именно вашей версии `psql`.

### 1.2. Второй отзыв того же студента

У Анны уже есть отзыв на мероприятие `1`. Ограничение
`reviews_event_user_uq` запрещает второй отзыв того же студента на то же мероприятие.

```sql
INSERT INTO reviews (event_id, user_id, rating, text)
VALUES (1, 4, 3, 'Второй отзыв');
```

Ожидаемый вывод PostgreSQL:

```text
ERROR:  duplicate key value violates unique constraint "reviews_event_user_uq"
DETAIL:  Key (event_id, user_id)=(1, 4) already exists.
```

### 1.3. Отзыв на несуществующее мероприятие

Внешний ключ `reviews_event_fk` не позволяет указать мероприятие, которого нет.

```sql
INSERT INTO reviews (event_id, user_id, rating, text)
VALUES (999999, 4, 5, 'Отзыв на несуществующее мероприятие');
```

Ожидаемый вывод PostgreSQL:

```text
ERROR:  insert or update on table "reviews" violates foreign key constraint "reviews_event_fk"
DETAIL:  Key (event_id)=(999999) is not present in table "events".
```

> Для отчёта желательно выполнить три команды в своём `psql` и вставить фактический вывод
> вместо блока с `Ожидаемый вывод`, потому что формат `Failing row contains` может отличаться
> между версиями PostgreSQL.

## 2. Можно ли выразить правило про автора отзыва ограничением таблицы?

Правило звучит так:

> Оставить отзыв может только тот, кто был записан на мероприятие, и только после его окончания.

Целиком выразить это обычным `CHECK`-ограничением таблицы `reviews` нельзя. `CHECK` проверяет
значения текущей строки и не предназначен для проверки существования подходящей записи
в другой таблице (`registrations`) или сравнения с текущим временем и данными другого
мероприятия.

Первая часть правила зависит от связи `reviews` → `registrations`: нужно проверить, существует
ли активная запись этого пользователя на это мероприятие. Вторая часть зависит от
`events.ends_at` и текущего времени.

Такую проверку следует выполнять на сервисном уровне приложения перед `INSERT` в `reviews`.
Дополнительно её можно защищать на уровне базы данных триггером или отдельной процедурой,
если требуется гарантия даже при прямом доступе к БД. Обычный `CHECK` для этого не подходит.

## 3. Гонка за BR-3: два одновременных INSERT

Для эксперимента используются два независимых окна `psql`.

### Сценарий A — COMMIT

В обоих окнах выполняется:

```sql
BEGIN;
```

Затем в окне A:

```sql
INSERT INTO registrations (event_id, user_id, status)
VALUES (2, 6, 'active');
```

В окне B выполняется тот же запрос:

```sql
INSERT INTO registrations (event_id, user_id, status)
VALUES (2, 6, 'active');
```

#### Наблюдение

| Шаг | Окно A | Окно B |
|---|---|---|
| 1 | `BEGIN` | — |
| 2 | `INSERT` — строка вставлена | `BEGIN` |
| 3 | — | `INSERT` ожидает завершения транзакции A |
| 4 | `COMMIT` | после `COMMIT` получает ошибку уникальности |

Ожидаемый результат в окне B:

```text
ERROR:  duplicate key value violates unique constraint "registrations_one_active"
DETAIL:  Key (event_id, user_id)=(2, 6) already exists.
```

Причина ожидания: у частичного уникального индекса `registrations_one_active` две
конкурирующие транзакции не могут независимо подтвердить одинаковую уникальную пару.
Вторая проверка ждёт решения первой транзакции, потому что первая ещё не сделала
`COMMIT` или `ROLLBACK`. После `COMMIT` первой транзакции строка становится видимой
для проверки уникальности, и второй `INSERT` завершается ошибкой.

### Сценарий B — ROLLBACK

Сначала повторяем эксперимент для Дениса:

```sql
BEGIN;
```

В окне A:

```sql
INSERT INTO registrations (event_id, user_id, status)
VALUES (2, 7, 'active');
```

В окне B:

```sql
BEGIN;

INSERT INTO registrations (event_id, user_id, status)
VALUES (2, 7, 'active');
```

Окно B снова ждёт завершения транзакции A.

Теперь в окне A вместо `COMMIT`:

```sql
ROLLBACK;
```

#### Наблюдение

| Шаг | Окно A | Окно B |
|---|---|---|
| 1 | `BEGIN` | — |
| 2 | `INSERT` — строка вставлена | `BEGIN` |
| 3 | — | `INSERT` ожидает |
| 4 | `ROLLBACK` | после отката A `INSERT` завершается успешно |

После этого в окне B:

```sql
COMMIT;
```

Итог: строка Дениса успешно сохраняется, потому что вставка A была отменена и уникальный
конфликт исчез.

### Почему здесь не нужен `FOR UPDATE`

В этом эксперименте две транзакции вставляют одну и ту же пару `(event_id, user_id)`,
а уникальность уже защищена индексом `registrations_one_active`. PostgreSQL сам
сериализует проверку уникального ограничения: вторая вставка ждёт результата первой
транзакции и затем либо получает ошибку, либо может продолжить после `ROLLBACK`.

В гонке за последнее свободное место этого недостаточно. Там две транзакции могут
обе увидеть свободную вместимость, после чего обе попытаться записаться. Поэтому
нужно атомарно защитить чтение и изменение количества доступных мест, например,
заблокировав строку мероприятия через `SELECT ... FOR UPDATE`.
