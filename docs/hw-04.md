## Часть 1. Отмена записи

Добавил эндпоинт:

`DELETE /api/events/{event_id}/registrations/{user_id}`

Работает он следующим образом:

- если запись активная и мероприятие ещё не началось — возвращается `204`;
- сама строка из таблицы `registrations` не удаляется, у неё меняется `status` на `cancelled`;
- если активной записи нет — возвращается `404`;
- если мероприятие уже началось — возвращается `409`.

Также добавил возможность снова записаться:

`POST /api/events/{event_id}/registrations/{user_id}`

Если у пользователя уже есть отменённая запись, новая строка в таблицу не добавляется. Существующая запись снова становится `active`.

Для этого используется частичный уникальный индекс `registrations_one_active`. Он запрещает несколько активных записей одного пользователя на одно мероприятие, но позволяет хранить старые отменённые записи.

### Проверка

1. Записать Бориса на мероприятие:

```text
POST /api/events/2/registrations/5
```

2. Отменить запись:

```text
DELETE /api/events/2/registrations/5
```

3. Проверить таблицу `registrations`. Строка должна остаться, но её `status` должен быть `cancelled`.

4. Снова записать Бориса:

```text
POST /api/events/2/registrations/5
```

5. Проверить таблицу ещё раз. Статус записи должен снова стать `active`.

## Часть 2. Свободные места и N+1

В `EventRead` добавил поле:

```text
free_seats
```

Оно показывает количество свободных мест:

```text
capacity - количество активных записей
```

Для имеющихся демо-данных получается:

- лекция про Яндекс — `38`;
- турнир по шахматам — `63`;
- мастер-класс по Git — `1`.

Количество свободных мест рассчитывается прямо в SQL-запросе с помощью коррелированного подзапроса `COUNT`.

Поэтому для каждого мероприятия не выполняется отдельный запрос на подсчёт записей.

Для `GET /api/events` получается два основных SQL-запроса:

1. запрос для получения `total`;
2. запрос для получения списка мероприятий вместе с `free_seats`.

То есть получается **2 запроса на страницу**, а не `1 + N`.

Если бы для каждого мероприятия отдельно делался `COUNT` записей, при `N` мероприятиях получилось бы:

```text
1 + N
```

запросов.

Для `GET /api/events/{id}` мероприятие и `free_seats` получаются одним SQL-запросом.

### Проверка через SQL_ECHO

Перед запуском API можно включить вывод SQL-запросов:

```powershell
$env:SQL_ECHO="1"
```

После этого запустить приложение:

```powershell
python -m uvicorn app.main:app --reload --app-dir api
```

Затем открыть:

```text
GET /api/events?size=20
```

В консоли должны быть видны SQL-запросы. Для получения страницы мероприятий используется один запрос на `COUNT` и один запрос на сам список с подсчётом активных записей.

## Часть 3. Теги через миграцию

Добавил систему тегов для мероприятий.

Созданы:

- модель `Tag`;
- таблица `tags`;
- таблица связи `event_tags`;
- связь `Event.tags`;
- связь `Tag.events`.

Для тегов сделал следующие ограничения:

- название тега должно быть уникальным;
- одна и та же пара `event_id` + `tag_id` не может добавляться несколько раз;
- при удалении мероприятия удаляются связанные записи из `event_tags`;
- при удалении тега также удаляются связанные записи.

Миграция находится здесь:

`api/migrations/versions/2026_11_20_1400-7f4b2c1d9a10_add_tags.py`

Она создаёт таблицы:

```text
tags
event_tags
```

При откате удаляются только эти две таблицы, остальные таблицы базы данных не затрагиваются.

### Проверка миграции

Из папки `api`:

```powershell
python -m alembic upgrade head
```

Посмотреть текущую ревизию:

```powershell
python -m alembic current
```

Для проверки отката:

```powershell
python -m alembic downgrade -1
```

После этого таблиц `tags` и `event_tags` быть не должно.

Чтобы вернуть миграцию:

```powershell
python -m alembic upgrade head
```

После этого таблицы снова должны появиться.

### Демо-данные

В `api/app/seed.py` добавлены четыре тега:

- `лекция`;
- `IT`;
- `турнир`;
- `кино`.

Связи между мероприятиями и тегами:

| Мероприятие | Теги |
|---|---|
| Как устроен поиск Яндекса | лекция, IT |
| Мастер-класс: Git без боли | IT |
| Турнир по шахматам | турнир |
| Кино: «Сталкер» | кино |

Проверить их можно запросом:

```sql
SELECT e.title, string_agg(t.name, ', ' ORDER BY t.name) AS tags
FROM events e
JOIN event_tags et ON et.event_id = e.id
JOIN tags t ON t.id = et.tag_id
GROUP BY e.id, e.title
ORDER BY e.starts_at;
```

## Часть 4. Гонка за аудиторию

Для проверки конкурентных запросов добавил скрипт:

`api/scripts/race_rooms.py`

Он одновременно отправляет три запроса `POST /api/events` на одну и ту же аудиторию и на один интервал времени.

Запуск:

```powershell
python api/scripts/race_rooms.py
```

В результате одно мероприятие должно успешно создаться:

```text
201 Created
```

а остальные два должны получить:

```text
409 Conflict
```

То есть ожидаемый результат:

| Запрос | Результат |
|---|---|
| A | `201 Created` |
| B | `409 Conflict` |
| C | `409 Conflict` |

Текст ошибки `409` может отличаться.

В одном случае запрос успевает увидеть уже созданное мероприятие и получает сообщение примерно такого вида:

```text
Аудитория «Ауд. 214» занята: ...
```

В другом случае несколько запросов одновременно проходят обычную проверку, потому что ещё не видят изменения друг друга. Тогда конфликт уже обнаруживает PostgreSQL при попытке сохранить данные:

```text
Аудиторию только что заняли на это время
```

Это происходит из-за одновременного выполнения запросов.

Самой проверки через `SELECT` недостаточно, потому что два параллельных запроса могут одновременно проверить аудиторию и оба решить, что она свободна.

Поэтому окончательно ситуацию контролирует ограничение `events_room_no_overlap` в PostgreSQL.

Если убрать это ограничение, несколько параллельных запросов потенциально могли бы создать мероприятия с пересекающимися интервалами в одной аудитории.

В итоге база данных сама не позволяет сохранить конфликтующие записи, даже если несколько запросов одновременно прошли предварительную проверку.
