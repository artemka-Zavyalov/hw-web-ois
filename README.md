## 1. Цель и границы

### 1.1. Проблема
Запись на консультации сейчас легко вести в переписке или таблице, из-за чего преподаватель может не видеть актуальную занятость слотов, а студент — не понимать, свободно ли выбранное время. При одновременной записи двух студентов один слот может быть занят дважды. Переносы и отмены теряются среди сообщений, поэтому преподавателю приходится вручную сверять список записавшихся.

### 1.2. Цель
Система должна хранить расписание консультационных слотов, показывать студентам только актуально доступное время и не допускать двойной записи на один слот. Преподаватель должен управлять своими слотами и видеть список записавшихся.

### 1.3. Что входит
- создание преподавателем консультационных слотов;
- просмотр доступных слотов студентами;
- запись студента на свободный слот;
- отмена записи студентом;
- перенос или отмена слота преподавателем;
- просмотр списка записавшихся преподавателем.

### 1.4. Что сознательно НЕ входит
| Не делаем | Почему |
|---|---|
| Видеоконференции внутри системы | Для проведения встречи можно использовать существующие сервисы, а встроенный видеомодуль увеличит объём проекта. |
| Автоматическую оценку студента преподавателем | Оценивание не связано с задачей бронирования времени консультации. |
| Интеграцию с электронным журналом и учебными планами | Для первой версии достаточно самостоятельного расписания; интеграция потребует дополнительных источников данных и прав доступа. |
| Онлайн-оплату консультаций | Консультации в системе считаются бесплатными, поэтому платёжный контур не нужен. |

## 2. Роли

| Роль | Кто это | Что может |
|---|---|---|
| Студент | Пользователь, которому нужна консультация | Просматривать доступные слоты, записываться, отменять свою запись, просматривать свои записи. |
| Преподаватель | Пользователь, проводящий консультации | Создавать и изменять свои слоты, закрывать слот, видеть записавшихся, отменять консультацию. |
| Администратор | Ответственный за работу системы | Управлять пользователями и ролями, просматривать все слоты и записи, блокировать некорректные данные. |

## 3. Сценарии

**С-1. Создание слота преподавателем.**
1. Преподаватель авторизуется.
2. Выбирает дату, время начала, продолжительность и формат консультации.
3. Система проверяет, что у преподавателя нет пересекающегося слота.
4. При успешной проверке система создаёт слот со статусом `OPEN`.
5. Система возвращает созданный слот с идентификатором.

**С-2. Запись студента.**
1. Студент открывает список доступных слотов.
2. Выбирает свободный слот.
3. Отправляет запрос на запись.
4. Система в транзакции проверяет, что слот всё ещё свободен.
5. Система создаёт запись студента и переводит слот в состояние `BOOKED`.
6. Студент получает подтверждение.

**С-3. Отмена записи.**
1. Студент открывает свою запись.
2. Нажимает отмену.
3. Система проверяет право студента отменять именно свою запись.
4. Система меняет статус записи на `CANCELLED`.
5. Слот снова становится доступным, если консультация ещё не началась.

**С-4. Отмена консультации преподавателем.**
1. Преподаватель открывает свой слот.
2. Выбирает отмену.
3. Система меняет статус слота на `CANCELLED`.
4. Все активные записи на этот слот переводятся в `CANCELLED`.
5. Студенты видят, что консультация отменена.

## 4. Бизнес-правила и функциональные требования

| № | Правило | Где обеспечивается |
|---|---|---|
| BR-1 | На один слот может существовать не более одной активной записи студента. | БД: уникальное ограничение на `slot_id` для активной записи + транзакция сервисного слоя. |
| BR-2 | Студент не может записаться на слот со статусом `BOOKED`, `CANCELLED` или `DONE`. | Сервисный слой. |
| BR-3 | Студент может отменить только собственную активную запись. | Сервисный слой и проверка прав. |
| BR-4 | Преподаватель может изменять только собственные слоты. | Проверка прав в API/сервисном слое. |
| BR-5 | Время окончания слота должно быть позже времени начала. | Валидация API и сервисный слой. |
| BR-6 | Два слота одного преподавателя не могут пересекаться по времени. | Сервисный слой + проверка перед записью в БД. |
| BR-7 | Запись на консультацию, которая уже началась, запрещена. | Сервисный слой при создании записи. |

### Одновременные запросы
BR-1 и BR-6 могут нарушиться при наивной реализации.

- **BR-1:** два студента одновременно отправляют POST на один свободный слот. Если оба сначала прочитают `OPEN`, а затем отдельно создадут запись, оба могут получить положительный результат. Поэтому создание записи должно выполняться в транзакции с блокировкой/уникальным ограничением.
- **BR-6:** преподаватель одновременно создаёт два пересекающихся слота из двух запросов. Если оба запроса проверяют отсутствие пересечения до сохранения, каждый может увидеть свободное состояние. Нужна транзакционная проверка и защита на уровне БД/сервисного слоя.

### Критерии приёмки

**AC-1 — двойная запись.**
- Исходные данные: слот `S1` имеет статус `OPEN`.
- Действие: одновременно отправлены два запроса записи от разных студентов.
- Результат: только один запрос получает `201 Created`, второй получает `409 Conflict`; в БД остаётся одна активная запись.

**AC-2 — запись на занятый слот.**
- Исходные данные: слот `S2` имеет статус `BOOKED`.
- Действие: студент отправляет POST `/api/slots/S2/book`.
- Результат: `409 Conflict`, состояние слота и существующей записи не меняется.

**AC-3 — отмена чужой записи.**
- Исходные данные: запись принадлежит студенту `U1`.
- Действие: студент `U2` отправляет запрос отмены записи `R1`.
- Результат: `403 Forbidden`, статус `R1` остаётся активным.

## 5. Нефункциональные требования

| Область | Требование (проверяемое) |
|---|---|
| Производительность | 95% запросов чтения списка слотов должны обрабатываться не дольше 300 мс при 50 одновременных пользователях. |
| Доступность | В рабочем окружении API должно быть доступно не менее 99% времени в месяц, исключая заранее объявленные работы. |
| Безопасность | После 5 подряд неуспешных попыток входа учётная запись блокируется на 15 минут. |
| Валидация | 100% входящих запросов на создание/изменение слотов проходят серверную валидацию обязательных полей и временных интервалов. |
| Резервное копирование | Резервная копия БД создаётся не реже одного раза в сутки и хранится минимум 7 дней. |

## 6. Модель данных

### Сущности

**User**
- `id` — UUID, PK
- `full_name` — строка
- `email` — строка, UNIQUE
- `password_hash` — строка
- `role` — `STUDENT | TEACHER | ADMIN`

**ConsultationSlot**
- `id` — UUID, PK
- `teacher_id` — UUID, FK → `User.id`
- `start_at` — datetime
- `end_at` — datetime
- `format` — `ONLINE | OFFLINE`
- `location` — строка, nullable
- `status` — `OPEN | BOOKED | CANCELLED | DONE`

**Booking**
- `id` — UUID, PK
- `slot_id` — UUID, FK → `ConsultationSlot.id`
- `student_id` — UUID, FK → `User.id`
- `status` — `ACTIVE | CANCELLED`
- `created_at` — datetime
- `cancelled_at` — datetime, nullable

### Связи
- `User (teacher) 1:N ConsultationSlot`.
- `User (student) 1:N Booking`.
- `ConsultationSlot 1:N Booking` технически допускает историю отмен, но только одна запись может быть `ACTIVE`.
- `ConsultationSlot` и `Booking` связаны через `slot_id`.

## 7. Архитектура

Система состоит из:
1. Web-клиента, который отправляет HTTP/JSON-запросы.
2. FastAPI-приложения с REST API, аутентификацией, валидацией и бизнес-логикой.
3. PostgreSQL, где хранятся пользователи, слоты и записи.
4. Reverse proxy для рабочего окружения.
5. Сервиса миграций БД.

Клиент → REST API → сервисный слой → PostgreSQL.

## 8. Выбор стека

### 8.1. Критерии
Критерии выбора: простота разработки учебного проекта, поддержка REST и валидации, удобство работы с PostgreSQL, возможность явно реализовать транзакции и ограничения БД.

### ADR-1. Язык и backend-фреймворк
- **Контекст.** Нужен REST API с валидацией и понятной документацией.
- **Варианты.** Python + FastAPI; Java + Spring Boot.
- **Решение.** Python + FastAPI.
- **Последствия.** Быстрее разработка и меньше шаблонного кода, встроенная OpenAPI-документация удобна для демонстрации. Цена решения — меньше опыта с большими корпоративными проектами по сравнению с Java/Spring.

### ADR-2. СУБД
- **Контекст.** Нужны ограничения уникальности, транзакции и надёжное хранение расписания.
- **Варианты.** PostgreSQL; SQLite.
- **Решение.** PostgreSQL.
- **Последствия.** Хорошо подходит для конкурентных запросов и ограничений БД. Цена — отдельный сервис БД и более сложная локальная настройка.

### ADR-3. Аутентификация
- **Контекст.** В системе есть разные роли и доступ к чужим/своим данным.
- **Варианты.** JWT; серверные сессии.
- **Решение.** JWT.
- **Последствия.** API остаётся stateless и удобно масштабируется. Цена — нужно самостоятельно реализовать обновление/отзыв токенов и аккуратно хранить секрет ключа.

## 9. API

Все запросы используют префикс `/api`, формат данных — JSON, время передаётся в ISO 8601. Ошибки возвращаются в формате `{"detail": "текст ошибки"}`.

| Метод и путь | Кто | Что делает |
|---|---|---|
| `GET /api/teachers/{teacher_id}/slots` | Студент | Получает доступные слоты преподавателя. |
| `POST /api/teachers/{teacher_id}/slots` | Преподаватель | Создаёт слот. |
| `GET /api/slots/{slot_id}` | Студент/преподаватель | Получает данные слота. |
| `POST /api/slots/{slot_id}/book` | Студент | Записывается на консультацию. |
| `DELETE /api/bookings/{booking_id}` | Студент | Отменяет свою запись. |
| `PATCH /api/slots/{slot_id}` | Преподаватель | Изменяет или закрывает свой слот. |
| `GET /api/teachers/{teacher_id}/bookings` | Преподаватель | Получает записи на свои консультации. |
| `POST /api/slots/{slot_id}/cancel` | Преподаватель | Отменяет консультацию. |

Основные коды:
- `200 OK` — успешное чтение/изменение;
- `201 Created` — создан новый ресурс;
- `400 Bad Request` — некорректные данные;
- `401 Unauthorized` — пользователь не авторизован;
- `403 Forbidden` — недостаточно прав;
- `404 Not Found` — ресурс не найден;
- `409 Conflict` — конфликт состояния, например слот уже занят;
- `422 Unprocessable Entity` — ошибка валидации входных данных.
